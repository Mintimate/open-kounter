# Blob 计数并发与恢复设计

## 本轮决定

继续使用 EdgeOne Cloud Functions 和 `@edgeone/pages-blob`，保留 `system/counters.json` 的 `2.1` 数据格式。读路径使用强一致模式；所有计数器修改仍通过 `_blobStore.js` 的统一锁入口执行。

本轮修复锁的两个确定问题：

- 获取失败只重试 SDK 的 `PreconditionFailedError`，业务回调抛出的冲突不再触发整段业务重放。
- 不再按 `expiresAt` 自动删除另一请求持有的锁。即使超时，旧请求仍可能在运行，删除锁会允许两次读改写重叠。等待耗尽返回业务失败，绝不绕过锁写入。

`expiresAt` 现在仅用于诊断，不是抢占许可。正常请求在 `finally` 中检查所有者后释放锁。此方案优先保证互斥，代价是函数被终止或释放锁失败后，锁可能遗留，需要维护恢复；它不是具有自动故障恢复能力的分布式租约。

## 能力边界

当前 SDK 的强一致读保证读到已写入的数据；`onlyIfNew` 可以竞争创建一个不存在的 Key。公开接口没有原子递增、基于 ETag 的条件覆盖/删除和跨文档事务。因此：

- 强一致读不能让整个“读 → 加一 → 写”变成原子操作。
- 进程内互斥只覆盖一个实例，无法协调多个 Cloud Functions 实例。
- 续租、延长 TTL、写前再检查锁都不能在没有条件写或 fencing 校验的存储上严格防止过期写者覆盖。
- 分片可以降低竞争和文档大小，但不能单独解决同一分片的并发覆盖。
- 写入成功后响应丢失时，客户端无法确定是否已经计数；当前 `inc` 没有幂等键，自动重试可能重复计数。
- 导入先完整校验计数数据和域名配置，再覆盖计数文档；不会预先删除旧计数文档。计数文档与域名配置、旧迁移的凭证文档仍是多次写入，不保证一起提交或一起回滚。

参考：[Blob 官方接口](https://pages.edgeone.ai/document/blob-storage)、[Cloud Functions 限制](https://pages.edgeone.ai/document/cloud-functions)。部署前还应核对所用 SDK 和平台的条件写行为。

## 遗留锁恢复

1. 暂停对应 Store 的所有写入口，包括计数、管理、初始化和迁移；确保旧部署也不能继续写入。
2. 根据函数日志确认持锁请求及全部在途写请求已结束，考虑平台执行时限和网络请求的完成状态。不能仅依据 `expiresAt` 或固定等待时间判定安全。
3. 备份相关 Blob 文档，读取锁的 `requestId`、`createdAt` 与实际业务状态，核对是否有已完成但未返回成功的操作。
4. 仅清理已确认遗留的具体锁，再恢复写流量；不要批量删除 `locks/` 或整个 Store。

代码不会自动进行这些外部维护操作。

## 一次性认证凭证

Challenge、OIDC state/session 和管理凭证通过 `auth/consumed/<编码后的完整文档 Key>` 的 `onlyIfNew` 写入选出唯一消费者，然后删除原凭证。消费前后均检查过期时间；回执不会像租约一样被自动抢占。

回执只保存 `expiresAt` 和 `consumedAt`，不含密钥。当前没有自动垃圾回收任务；维护时仅在原凭证过期且确认没有在途消费请求后清理对应回执。旧版未经过验签生成的管理凭证、缺少新校验上下文的 Challenge 和 OIDC Session 会被拒绝，用户重新发起登录即可。

## Passkey 原始 Challenge 回收

新建 Challenge 使用独立随机 ID 和 `onlyIfNew`，新流程不续期、复用或删除其它流程的 ID。前端在中断时尽力按本次 ID 取消；服务器通过原有消费回执保证同一 Challenge 只能成功消费一次。不同流程可并行，凭证计数器更新仍使用用户锁，严格计数器不接受已被更新值超越的旧断言。注册提交也串行执行，保持重新绑定替换旧凭证的语义。

管理员可调用 `POST /api/maintenance/challenges`，携带现有 Bearer Token，每次最多检查 100 条，仅删除已过期至少 60 秒的 `passkey/challenges/` 原文档。扫描断点保存在 `system/maintenance/passkey-challenges.json`：`cursor` 为 `null` 或 `{ page, afterKey }`，分别记录 SDK 原始游标与本页已处理位置；`updatedAt` 记录更新时间。完成全扫后断点归零。

这不是消费回执回收：`auth/consumed/` 仍保留。已完成消费的验证使用内存中的 Challenge；未完成消费的过期请求会被过期检查拒绝。删除过期原文档不会撤销已完成消费的验证，也不会允许相同凭证重复消费。用户历史 `currentChallengeId` 字段不再承担单流程限制，扫描不修改用户文档；消费或取消同 ID 时才清理匹配的旧引用。

旧 KV 导入可能重写原 ID，因此清理和显式取消与迁移共用 `locks/legacy-migration.json`，禁止仅检查锁是否存在后无锁删除。回收只尝试获取一次锁，失败可稍后重试；不可自动清理遗留锁。回收约 10 秒后停止启动新的操作，但会等待已开始的读写完成再释放锁，不能把预算耗尽视为在途存储操作已经停止。函数仍可能因平台终止留下锁，恢复规则不变。

读取或删除暂时失败会保留重试位置，允许重复调用；坏 JSON 留存并跳过，下一轮扫描再检查。每次请求返回 `scanned`、`deleted`、`skipped`、`failed`、`hasMore`，`hasMore: true` 表示还需继续调用。过期仅决定文档失效，物理删除由取消、管理员手动调用触发。

## 高并发下一阶段选项

| 方案 | 原子更新与恢复 | 代价与待确认项 |
|---|---|---|
| Blob 保留全量文档与不可抢占锁（当前） | 正常运行互斥；故障时停止写入，维护恢复 | 所有目标共享锁；每次更新全量读写，吞吐受限 |
| Blob 不可变增量事件 | 用事件 ID + `onlyIfNew` 去重，避免覆盖同一计数文档 | 需要设计 `set/delete/import` 的 epoch、事件排序、快照和安全清理；读取与存储成本增大，必须验证 list 一致性 |
| 支持原子递增/事务的存储，Blob 用作备份 | 可使用存储原子操作、幂等记录和事务解决覆盖及重试 | 增加服务、凭证和费用，需要确认 EdgeOne 到该服务的网络与延迟 |
| 平台未来提供 CAS/原子计数能力 | 可基于真实条件覆盖或原子操作重做写路径 | 以正式 API 和故障测试为准，不能假设现在已支持 |

在确定并发量、可接受延迟/失败率、是否仅允许 Blob、能否增加服务前，不迁移现有计数 Schema。后续验证至少覆盖多实例争用、进程终止、写成功但响应丢失、重复请求、导入与增量写交错，以及备份恢复。
